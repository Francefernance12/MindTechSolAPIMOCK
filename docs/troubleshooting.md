# System Idiosyncrasies & Troubleshooting

This document explains some of the behaviors in the MindTechSolAPIMOCK system that might appear confusing at first glance.

## 1. Why is `client_id` sometimes `NULL` in the `jobs` table?

In the `jobs` table, the `client_id` column is optional (nullable). You will often see `NULL` (or `null` in JSON) for certain entries.

### Reasons for `NULL` client_id:
- **System-Wide Jobs**: Some scripts, like `sync_clients.py`, process the entire database or external files rather than acting on a single specific client. When a job represents a global action, it is logged with `client_id = NULL`.
- **Pre-Validation Failures**: If a job is intended for a specific client but fails before the client can be identified or validated in the database, the log entry might default to `NULL`.
- **Automated Syncs**: The daily/hourly sync jobs typically update many clients at once. Instead of creating 100 job logs (one for each client), the system logs one "Sync" event with a summary message and a `NULL` client ID.

### When should it NOT be `NULL`?
- **Manual Actions**: Actions performed via the UI or API for a specific client (e.g., "Generate Report for Client X") should always have a valid `client_id`.
- **Transaction Logs**: Test logs generated by `seed.py` that specifically test per-client logging.

## 2. What are the repetitive tests (CSV files)?

If you see repeated logs or files referencing "CSV tests," these are typically part of the **Data Integrity and Transaction Validation** suite.

### The "CSV" refers to `data/clients_sample.csv`
This file is the "Source of Truth" for the automated sync process. The system frequently "tests" its ability to read this file and sync it to the database.

### Why do they keep repeating?
1. **Seed Script Validation**: Every time `python seed.py` is run, it executes several hardcoded "Transaction Tests" at the end of the script to ensure that the database's rollback mechanism is working correctly.
2. **Scheduled Syncs**: The `backend/scheduler.py` (APScheduler) is configured to run the `sync_clients.py` script periodically. Each run creates a new job log and a new JSON report in `logs/syncReports/`.
3. **Idempotency Testing**: The system uses `INSERT OR IGNORE` and `ON CONFLICT` logic. The "repeating" tests ensure that running the same import multiple times doesn't create duplicate data, but instead updates existing records correctly (Upsert).

### How to distinguish them:
- **`seed.py` logs**: Usually contain messages like `"TRANSACTION TEST: ..."` or `"This should roll back"`. These are intended to verify that the system handles errors gracefully.
- **`sync_clients.py` logs**: Usually contain messages like `"Synced X, failed Y"`. These are actual heartbeat logs of the background sync process.

---

## 3. Automated Reports (`logs/syncReports/`)

You may notice a large number of JSON files in `logs/syncReports/`. 
- **Purpose**: These provide a detailed audit trail of every automated sync attempt.
- **Cleanup**: In a production environment, these would be rotated or archived. In this mock, they are kept so you can verify the scheduler is working.
